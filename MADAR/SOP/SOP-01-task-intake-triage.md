# SOP-01 — استقبال الطلبات والفرز (Task Intake & Triage)

| | |
|---|---|
| **الحالة** | معتمد |
| **المالك** | صاحب المشروع |
| **ينطبق على** | كل طلب قادم من صاحب المشروع أو عميل أو وكيل ذكاء اصطناعي |
| **المرجع الأعلى** | `AGENTS.md` — هذا الإجراء لا يُنشئ ولا يُلغي أي قاعدة فيه |
| **الناتج** | ملف قضية واحد داخل `MADAR/bug issues/` |
| **التبعية** | يشير إلى SOP-02..SOP-10 (**لم تُنشأ بعد**)، وإلى `policies/issue-lifecycle-priorities.md` (**غير موجود بعد**) |

> **قاعدة هذا الإجراء:** لا يبدأ أي تعديل على `lib/` قبل تصنيف الطلب عبر هذا الإجراء، إلا لو كان الطلب من نوع حادثة إنتاج P1 — عندها يبدأ استجابة الحادثة فورًا بالتوازي مع إكمال الفرز.

---

## A. متى يُستخدم هذا الإجراء

يُطبَّق إلزاميًا على كل طلب لا يحمل تصنيفًا واضحًا، وعلى كل طلب جديد لم يسبق تصنيفه.

**استثناء وحيد:** طلب صريح وموثّق من صاحب المشروع يحمل تصنيفًا ونطاقًا ومعيار قبول — فيُسجَّل مباشرة بالحالة `open` ويبدأ مساره من قالبه.

### أنواع الطلبات السبعة

| الرمز | النوع | التمييز |
|---|---|---|
| **A** | حادثة إنتاج / خلل حرج | خلل **حاصل فعلًا عند عميل في بيئة إنتاج**: توقف، فقدان أو تشوّه بيانات، خطأ محاسبي ظاهر، فساد مالي، أو ثغرة أمنية |
| **B** | عيب عادي | سلوك مخالف للمواصفة، في بيئة تطوير أو اختبار، ولا يوقف عمل عميل |
| **C** | ميزة جديدة | سلوك غير موجود أصلًا |
| **D** | تعديل سلوك قائم | السلوك موجود ويعمل، والمطلوب تغييره |
| **E** | Refactoring / ديون تقنية | تغيير داخلي بلا تغيير في السلوك المرئي |
| **F** | بحث أو سؤال معلوماتي | لا يُنتج كودًا؛ ناتجه وثيقة أو إجابة مسنَدة |
| **G** | طلب عميل بنطاق أو تسعير | يحتاج قرار تجاري قبل أي كود |

**فاصل حاسم بين A و B:** هل يوجد عميل متأثر الآن؟ إن نعم ← A. إن كان الخلل في بيئة التطوير فقط، أو موجود ولم يُبلّغ عنه أحد ← B.

### B.2 إلزامية حسب نوع الطلب

| النوع | إضافات إلزامية |
|---|---|
| A | الأثر على الإنتاج · عدد العملاء المتأثرين · هل توجد بيانات مالية متضررة |
| B | خطوات إعادة الإنتاج · النتيجة المتوقعة مقابل الفعلية · التكرار |
| C · D · E | معايير القبول (AC) بصيغة قابلة للاختبار |
| F | السؤال الدقيق والمصدر المطلوب الرجوع إليه |
| G | بنود العقد · ما هو مشمول · ما يحتاج إضافة مدفوعة |

### B.3 معلومات قد تكون غير متاحة أثناء الفرز

هذه **لا تمنع** إنشاء الملف، لكن تُوسم بـ«مطلوب لاحقًا» وتُجمع قبل التنفيذ:

- خطوات إعادة الإنتاج الدقيقة (قد تتطلب تواصلًا مع العميل)
- حجم البيانات المتأثرة
- ما إذا كان السلوك الحالي **مقصودًا** أم عيبًا
- وجود workaround فعلي

> قاعدة `AGENTS.md` §7: أي افتراض غير مؤكد يُسأل عنه ولا يُخمَّن.

## C. التصنيف والتوجيه

| النوع | الأولوية الافتراضية | الإجراء التالي | القالب | موافقة صاحب المشروع مطلوبة |
|---|---|---|---|---|
| **A** حادثة إنتاج | **P1** | **SOP-09 فورًا** (استجابة حادثة) | `_template-bug.md` | ✅ إلزامية قبل أي تغيير كود |
| **B** عيب عادي | P2 / P3 | **SOP-02** | `_template-bug.md` | ❌ لا، إلا لو مستطقة حساسة (§E) |
| **C** ميزة جديدة | P3 | **SOP-03** | `_template-feature.md` | ✅ قبل التنفيذ + معايير القبول |
| **D** تعديل سلوك | P2 / P3 | **SOP-04** | `_template-feature.md` | ✅ — لأن السلوك الحالي قد يكون مقصودًا |
| **E** ديون تقنية | P4 | **SOP-04** | `_template-feature.md` | ❌ للعناصر البسيطة، ✅ للتي تمس بنية النظام |
| **F** بحث | P4 | **بلا كود** | `_template-feature.md` اختياري | ❌ |
| **G** طلب عميل | يُحدَّد بعد النطاق | **SOP-05 أولًا** | `_template-feature.md` + القسم 7 | ✅ إلزامية قبل أي كود |

### C.1 مسار حادثة P1 لا يمرّ كعيب عادي

عند تصنيف طلب كـ **A**:

1. **لا يُنتظر اكتمال الفرز.** تبدأ استجابة الحادثة فورًا (احتواء، نسخ احتياطي، حفظ أدلة).
2. يُسجَّل ملف القضية بالتوازي ويبدأ بـ`status: in-progress` مع الأولوية P1.
3. **لا يُكتب أي إصلاح كود قبل قرار صريح من صاحب المشروع** + **نسخة احتياطية مؤكدة**.
4. يليه تحليل جذري إلزامي؛ ولا يُغلق قبل تقرير postmortem (SOP-09).

> **تبعية غير مُنجزة:** `SOP-09-incident-postmortem.md` **لم يُنشأ بعد**. حتى إنشائه، أوقف تصحيح P1 عند قاعدة: احتواء فوري → حفظ أدلة → إبلاغ صاحب المشروع → قرار. ولا تبنِ إجراء استجابة كامل افتراضيًا داخل هذا الملف.

## D. تعريفات الأولوية

الأولوية تُشتق من **الأثر**، لا من نبرة الطلب. لا تُصنَّف P1 لمجرد أن صاحب المشروع كتب «عاجل».

| الأولوية | المعيار الحاكم | أمثلة |
|---|---|---|
| **P1** | خلل شاغل في الإنتاج، **أو** خطر سلامة بيانات/مالية/أمانية | توقف التطبيق عند عميل · تلف قاعدة بيانات · اختلاف في رصيد/فاتورة نقدية في بيئة حقيقية · كشف مفتاح أو تجاوز ترخيص |
| **P2** | مسار أساسي معطّل **وبلا** حل بديل، ولا يوجد عميل متوقف الآن | فشل إنشاء فاتورة بيع · فشل حفظ راتب · فشل استرجاع نسخة احتياطية · تعطّل حضور ZKTeco يمنع تسجيل الحضور |
| **P3** | خلل أو تحسين **له** حل بديل، أو عيب محدود الأثر | خطأ في تنسيق تقرير · طباعة فاتورة ناقصة حقل · بطء في شاشة جانبية |
| **P4** | لا أثر على العمل اليومي؛ ديون تقنية، بحث، أو تحسين مستقبلي | تنظيف كود · رفع تغطية اختبار لمWxRFected مسار · مقارنة مكتبات |

**قواعد منع التداخل:**

- تأثير بيانات/مالية/صحّة = لا يقل عن P2 مهما كان التكرار.
- «فيه workaround» يخفض الأولوية **درجة واحدة فقط**، ولا يُنزل P1 إلى P3 أبدًا.
- نوع G لا يُعطى أولوية تنفيذ قبل قرار النطاق؛ أولويته = أولوية القرار.
- إعادة التصنيف مسموحة عند تغيّر الأدلة، ويجب تسجيل السبب في سجل الحالة.

## E. قواعد التوقف والسؤال

> **تمييز أساسي:** التشخيص للقراءة فقط (فحص، بحث، قراءة سجلات، كتابة اختبار فاشل) **مسموح دائمًا** في المناطق الحساسة. ما يحتاج موافقة هو **التنفيذ** الذي يغيّر سلوكًا أو بيانات.

### E.1 يتوقف قبل التنفيذ — المناطق الحساسة

| المنطقة | يُسمح بالقراءة والتشخيص | يتطلب موافقة صاحب المشروع قبل التنفيذ |
|---|---|---|
| ترخيص / ربط الجهاز | فحص الكود، مراجعة `lib/services/license_manager.dart` و`hardware_id_service.dart` | أي تعديل على التحقق أو التوقيع أو التخزين الآمن · **وممنوع منعًا باتًا تمرير مفاتيح حقيقية في اختبارات** |
| رواتب / حضور | تشغيل الاختبارات القائمة وقراءة الكود | أي تعديل على قاعدة حساب أو استقطاع |
| تصنيع / BOM / استهلاك مخزون | فحص تكامل BOM | أي تعديل على وصفة أو استهلاك يغيّر كميات |
| دفتر حسابات / فواتير / نقد / إقفال يوم | فحص التقارير والحسابات | أي تعديل على قيد أو رصيد أو إقفال |
| نسخ احتياطي / استرجاع | **قراءة فقط**: فحص القوائم والاختبارات | أي تعديل على مفتاح تشفير أو تنسيق ملف نسخة أو قائمة جداول |
| مزامنة / offline | فحص منطق التعارض | أي تعديل على سياسات حل التعارض |
| مخطط قاعدة البيانات / migrations | قراءة `app_database.dart` وخطوات `onUpgrade` | **أي** تعديل على migration — `AGENTS.md` §4.3 يمنع تعديل step مُطبَّقة، و`§4.4` يفرض التبرير قبل أي جدول جديد |

### E.2 يتوقف ويسأل في الحالات الآتية

1. غموض في معايير القبول أو في السلوك المطلوب.
2. طلب عميل بنطاق أو تسعير غير محسوم.
3. أي مساس بالـ**base flavor** أثناء عمل flavor آخر (`AGENTS.md` §5).
4. طلب تغيير جدول جديد.
5. **تعارض مع عمل جارٍ**: ملف مفتوح يعدّله وكيل آخر، أو تغييرات غير متوقعة في شجرة العمل أثناء التنفيذ.
6. أي طلب يخالف `AGENTS.md` §2 (تغيير state management أو ORM) أو §8 (الممنوعات).
7. ادّعاء اختبار لم يُنفَّذ فعلًا، أو رغبة في إعلان نجاح دون دليل.

### E.3 قاعدة التعارض مع وكيل آخر

قبل تعديل أي ملف: افحص حالة شجرة العمل. إن كان الملف معدَّلًا أو في طور تعديل من وكيل آخر ← **توقّف وأبلغ**، ولا تُكمل على أساس نسخة قديمة.

## F. مسموح وممنوع أثناء الفرز

### مسموح بلا موافقة

- القراءة والبحث في المستودع كاملًا.
- تشغيل اختبارات القراءة فقط وتحليلها.
- إنشاء وتعديل ملف القضية داخل `MADAR/bug issues/`.
- إنشاء فرع عمل/worktree جديد **باسم مهمة واضحة** ودون لمس فرع أو شجرة عمل تخص غيرك.
- أوامر Git للقراءة فقط: `git status` · `git log` · `git diff` · `git show` · `git branch --list`.

### ممنوع حتى بموافقة مسبقة صريحة

| الممنوع | السبب |
|---|---|
| أي تعديل على `lib/` أو `test/` أثناء الفرز | الفرز يسبق التنفيذ |
| `git checkout` · `git reset` · `git clean` · `git stash` · `git rebase` على فروع مشتركة | كسر عمل الوكلاء الآخرين |
| `git merge` · `git push` · `git commit` | خارج نطاق الفرز |
| تعديل أو تدوير مفاتيح تشفير النسخ الاحتياطي | يمنع استرجاع نسخ موجودة — انظر ملاحظة F.1 |
| تعديل migration مُطبَّقة | `AGENTS.md` §4.3 |
| تعديل `MADAR/SOP/` أو `AGENTS.md` أثناء مهمة غير مخصّصة لوثائقها | خارج النطاق |
| إرسال بيانات عميل حقيقية خارج المستودع | خصوصية |

### F.1 ملاحظة على مفاتيح النسخ الاحتياطي

المستودع يحتوي **ثلاثة مفاتيح تشفير ثابتة** موزّعة على خدمتين (`EnhancedBackupService` في `lib/services/` و`BackupService` في `lib/core/services/`)، وخدمة `EnhancedBackupService` تحتفظ بقائمة مفاتيح قديمة لتجربة فك التشفير عند الاسترجاع.

**القاعدة:** التدوير يُنجز **بالإضافة** (المفتاح الجديد في مقدمة القائمة مع الإبقاء على القديم)، لا بالحذف. تغيير المفاتيح **ليس جزءًا من أي SOP عادي**، ويُعالَج كطلب مستقل بموافقة صريحة. التفصيل في SOP-08 (غير مُنشأ بعد).

## H. دورة الحياة

### H.1 الحالات

`open → in-progress → review → done` مع `rejected` كحالة إنهاء بديلة.

| الانتقال | شرطه |
|---|---|
| `open → in-progress` | اكتمال الحقول الإلزامية + أنشئ فرع/Worktree للعمل |
| `in-progress → review` | اكتمال التحقق المطلوب في SOP المسؤول |
| `review → done` | مراجعة صاحب المشروع + الدمج في `integration/all-agents` |
| `→ rejected` | قرار صاحب المشروع مع ذكر السبب (طلب ملغى · مكرر خارج النطاق · غير قابل للتنفيذ) |

### H.2 تسجيل الانتقالات

- الحالة تُحدَّث **بحقل `status` داخل الملف نفسه**. لا تُنشأ مجلدات فرعية للتصنيف — الملف هو وحدة التتبع الوحيدة.
- كل انتقال يُسجَّل بصف واحد في قسم «سجل الحالة» (القسم 8 في القالب): التاريخ · من · التغيير.
- لا يُDuplicate التتبع في أي مكان آخر؛ ملف القضية هو المصدر الوحيد للحالة.
- الملفات المُنجزة تبقى في مكانها كسجل تاريخي.

**إلزام المزامنة:** بعد إنشاء أو تحديث أو إغلاق أي ملف `MADAR/bug issues/BUG-<رقم>-<slug>.md`، شغّل تلقائيًا (بدون أي توكنات/مفاتيح في المستودع؛ السكريبت يقرأها من إعدادات الجهاز):

```powershell
# تذكرة واحدة:
powershell -ExecutionPolicy Bypass -File "C:\Users\Momen\.gemini\config\scripts\sync_bug_to_github_and_notion.ps1" -File "MADAR/bug issues/BUG-<رقم>-<slug>.md"

# كل التذاكر دفعة واحدة:
powershell -ExecutionPolicy Bypass -File "C:\Users\Momen\.gemini\config\scripts\sync_bug_to_github_and_notion.ps1" -All
```

### H.3 معيار اكتمال الفرز

الفرز مكتمل ☐ كل الحقول الـ12 موجودة ☐ الأولوية مبررة ☐ المسار محدد ☐ موافقة المالك مسجّلة إن كانت مطلوبة ☐ `status` = `open`.

**عندها فقط** ينتقل التنفيذ إلى الإجراء التالي. التنفيذ **متوقف** قبل ذلك.
