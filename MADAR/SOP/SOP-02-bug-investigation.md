## A. معايير الدخول

لا يبدأ فحص أي عيب قبل تحقق واحد من الشرطين:

1. **وجود ملف قضية** في `MADAR/bug issues/` بالحالة `open` أو `in-progress`، أو
2. **إنشاؤه فورًا** عبر `SOP-01` قبل أي عمل تقني.

**بند إلزامي:** عيب من نوع **A** (حادثة إنتاج P1) **لا يمرّ عبر هذا الإجراء**. يُصنَّف فورًا ويبدأ استجابة الحادثة عبر SOP-09 بالتوازي مع إكمال الفرز. حتى إنشاء SOP-09، القاعدة الموقفة: احتواء فوري → حفظ أدلة → إبلاغ صاحب المشروع → قرار. **لا يبدأ إصلاح كود لـ P1 دون موافقة صريحة ونسخة احتياطية مؤكدة.**

## B. أسئلة الفحص قبل أي تعديل

يُجيب عنها صاحب البلاغ أو الوكيل بأدلة مرصودة، لا بالتخمين:

| السؤال | لماذا يهم |
|---|---|
| خطوات إعادة الإنتاج **بالترتيب**؟ | بدونها لا يمكن الحكم على الإصلاح |
| النتيجة المتوقعة مقابل الفعلية؟ | يحدد الانحراف بدقة |
| التكرار: دائمًا / أحيانًا / مرة واحدة؟ | يحدد هل هو race condition أو علة حالة |
| أي `flavor`؟ (base / vegetable / clothing) | يكشف ارتباطًا بالـ feature flags |
| نسخة التطبيق وبيئة التشغيل؟ | يربط بالـ regressions |
| هل يمس بيانات عميل حقيقية أو فلوسًا أو مخزونًا؟ | يفعّل التحقق الإضافي (القسم I) |
| ما الأثر التجاري؟ | يحدد الأولوية الحقيقية |
| هل يوجد workaround؟ | يؤثر على P2/P3 لا على P1 |
| متى بدأ بالضبط؟ | يفصل regression عن علة قديمة |

> **قاعدة بيانات العميل:** ممنوع منعًا باتًا نقل أسماء أو هواتف أو باركود أو مفاتيح ترخيص حقيقية إلى ملف القضية أو إلى أي مخرج اختبار. يُستخدم `test/fixtures/` (موجود) وبيانات وهمية.

## C. الفحص المبني على الأدلة

بالترتيب. **لا يبدأ أي تعديل كود قبل الخطوة 6.**

### 1) إعادة الإنتاج

- أعد إنتاج العطل محليًا إن أمكن.
- **الأفضل:** حوّله إلى **اختبار Dart فاشل** يُثبّت السلوك. هذا أقوى دليل متاح وأرخص وسيلة لمنع الانتكاس.
- إن تعذّرت إعادة الإنتاج: اجمع البدائل (الخطوة 2) ولا تُصلح بالتخمين.

### 2) تسجيل الأدلة

- Stack trace كامل ← موضع `file:line` الدقيق.
- قيم البيانات المعنية (ببيانات وهمية).
- السجل الزمني للأحداث داخل التطبيق.
- سجلات إن وُجدت، وسجل جلسات الحضور والمزامنة إن كان العطل متعلقًا بهما.

### 3) تحديد موضع الكود

- الملف والدالة والسطر.
- المسار الكامل من مدخل المستخدم حتى الحساب أو الاستعلام.

### 4) البحث عن implementations المكرّرة

هذا المستودع يحتوي منطقًا متكررًا في أكثر من مكان (حسابات الفواتير، مستحقات الرواتب، قيود الدفتر، منطق الإقفال). **قبل الإصلاح، ابحث عن النسخ الأخرى لنفس السلوك** حتى لا يصلح فرع ويظل الآخر معطوبًا.

```bash
# مثال: ابحث عن نفس المفهوم في كل الطبقات
rg "<اسم الدالة أو الحقل>" lib/
```

> إن وُجدت نسخ متعددة، سجلها في ملف القضية، واذكر أي نسخ تُصلح الآن وأيها تُؤجّل لملف قضية منفصل (القسم E).

### 5) فحص Regression — شرطي

**نفّذ فقط** إذا كان العطل حديثًا أو تغيّر بعد دمج، **و** إذا كانت شجرة العمل في حالة تسمح.

**المسار الآمن الافتراضي — أوامر قراءة فقط:**

```bash
git log --oneline -20 -- lib/<path>
git log -S "<مقطع الشك]" --oneline
git show <commit> -- lib/<path>
```

**تحذير مهم:** `git bisect` يعمل بتنقّل بين commits عبر `git checkout` — أي أنه **يغيّر حالة شجرة العمل**. في مستودع يتشاركه أكثر من وكيل، هذا يفسّر عملهم ويمسّ ملفات غيرك.

> 🚫 **لا يُشغَّل `git bisect` في شجرة العمل المشتركة أو على فرع مشغول.** إن لزم العزل بشكل قاطع، أنشئ **worktree جديدًا خاصًا بالتحقيق** على commit معروف، ونفّذ فيه. لا يُشغَّل `git bisect` إطلاقًا على `integration/all-agents`، ولا يُستخدم `git checkout` / `git reset` / `git clean` أثناء مهمة من هذا الإجراء.

إن تعذّر الفحصHistory: وثّق ذلك صراحة في ملف القضية واعتمد على إعادة الإنتاج بدلًا منه.

### 6) صياغة فرضية قابلة للاختبار

اكتب فرضية واحدة بصيغة قابلة للإبطال:

> «العطل يحدث لأن **[سلوك محدد]** في **`path:line`** بسبب **[سبب محدد]**، ويظهر عندما **[شرط قابل للملاحظة]**.»

- فرضية واحدة في كل مرة.
- اختبرها. إن دحضتها الأدلة → **ارجع للخطوة 2** ولا تبنِ إصلاحًا فوقها.

### 7) مراجعة الفرضية

- الفرضية تُعدَّل أو تُستبدل كلما تناقضت مع دليل جديد.
- لا يُعامَل تعديل غير مؤكد كأنه مؤكد.

### 8) توثيق السبب — أو إعلان عدم التأكد

انتقل إلى القسم D.

## D. توثيق السبب الجذري قبل التنفيذ

يُملأ القسم 4 من `MADAR/bug issues/_template-bug.md` **قبل** أي تعديل على الكود.

**المطلوب:**

- **السطحي:** ما يظهر على المستخدم.
- **الجذري:** `file:line` + لماذا يوجد الخلل أصلًا.
- **لماذا لم يمسكه الاختبار الموجود:** ثغرة التغطية.
- **هل هو Regression:** نعم/لا + الـcommit المتسبب إن عُرف.

**إذا لم يتأكد السبب بعد**، يُكتب صراحة:

> «لم يُأكد السبب الجذري بعد. الدليل الحالي: … . الفرضية المتبقية: … . قرار المتابعة: إصلاح تجريبي مدعوم باختبار فاشل — والمتابعة مشروطة بتثبيت فرضية أقوى.»

هذا مقبول. **غير المقبول** هو ادّعاء سبب جذري لم يُثبَت. الإصلاح التجريبي المدعوم باختبار فاشل أفضل من سبب مخترع.

## E. حدود الإصلاح

### E.1 الجوهري

| القاعدة | التفصيل |
|---|---|
| أصلح الجذري لا العَرَضي | إخفاء رسالة خطأ، أو `if` يتخطى الحالة، أو تخفيف تحقق — **ليس إصلاحًا** بدون سبب جذري موثّق |
| لا refactoring جانبي | إصلاح العطل فقط. أي تحسين مسكوت عنه → ملف قضية منفصل |
| عطل غير متصل → ملف منفصل | لا تُضمّ مخالفات عارضة في نفس التغيير |
| حافظ على البنية القائمة | قواعد الطبقات في `AGENTS.md` §3، والـDAO في §4.2 |
| لا تغيّر الـschema للهروب من عطل | تغيير المخطط لذلك قرار منفصل يحتاج موافقة صريحة |

### E.2 راجع `AGENTS.md` — لا تكرره

| القاعدة | المرجع |
|---|---|
| لا تغيّر state management ولا ORM | §2 |
| DAO/service لا widgets | §3 |
| soft delete هو الافتراضي | §4.2 |
| **migrations append-only — ممنوع تعديل step مُطبَّقة** | §4.3 |
| إعادة الاستخدام قبل أي جدول جديد | §4.4 |
| `AppFeatures` فقط كبوابة flavors | §5 |
| الذرّية في أي مسار مال/مخزون | §6 |
| مرحلة واحدة في المرة + سؤال عند الشك | §7 |
| الممنوعات الصريحة | §8 |

> هذا الجدول **إحالة فقط**. عند التعارض، `AGENTS.md` هو الحاكم ويُبلَّغ عن التعارض ولا يُعاد تعريفه هنا.

### E.3 موافقة مطلوبة قبل التنفيذ

- أي تعديل يمسّ **منطقة حساسة** بما يخالف السلوك التجاري القائم → `SOP-01` §E.
- أي تعديل على **base flavor** أثناء عمل flavor آخر.
- أي تغيير في **قاعدة محاسبية أو ضريبية** متعارف عليها.
- أي تعديل على **migration مُطبَّقة** — ممنوع حتى بموافقة؛ `AGENTS.md` §4.3 لا تسمح به أصلًا.

## F. الاختبار والتحقق

### F.1 الحد الأدنى لكل عطل

| الخطوة | الشرط |
|---|---|
| 1 | **اختبار انحدار** عند الإمكان — بنفس نمط المشروع القائم، لا بأسلوب جديد |
| 2 | تشغيل الملف/الحيزمة الفعلية و**تسجيل المخرج الحرفي** |
| 3 | `fvm flutter analyze` عند إمساس `lib/` |
| 4 | تسجيل ما تعذّر تشغيله **مع السبب** |

### F.2 مواقع الاختبارات القائمة — لا تخترع مسارًا جديدًا

| المسار | المحتوى |
|---|---|
| `test/unit/` | منطق الأعمال |
| `test/unit/dao/` | استعلامات DAO |
| `test/unit/services/` | الخدمات |
| `test/fixtures/` | بيانات وهمية للاختبار |
| `test/widget/` · `test/manual/` · `test/services/` | شاشات / اختبار يدوي / خدمات |

### F.3 أوامر التحقق

```bash
fvm flutter test test/unit/<file>.dart     # ملف محدد
fvm flutter test                            # الحزمة كاملة
fvm flutter analyze                         # تحليل ثابت
dart run build_runner build --delete-conflicting-outputs
```

**عن `build_runner` — شرطي وليس روتينيًا:** يُشغَّل **فقط** إذا كان التعديل يتطلب إعادة توليد كود Drift (تعديل `lib/core/database/tables/` أو `dao/` أو إضافة DAO إلى `app_database.dart`). تعديل داخل DAO أو service أو UI **لا يحتاجه**.

### F.4 قاعدة الصدق في الأدلة

> 🚫 لا يكتب أحد «اختُبر بنجاح» أو «تم التنفيذ» دون أمر مُنفَّذ ومخرج ملاحَظ ومسجَّل في القسم 6 من ملف القضية.

**وحالة `analyze` النظيف ليست دليلًا على صحة السلوك التجاري.** هي دليل على سلامة الأنواع فقط. أي فرق في الأرقام أو المخزون أو الرواتب لا تكشفه `analyze` إطلاقًا.

**وعند تعذّر التحقق** (بيئة غير متاحة، تحتاج جهازًا، تحتاج بيانات عميل محمية): يُوثَّق ذلك صراحة في القسم 6 مع سبب التعذّر، ويُوسم التقييم «تحقق جزئي» — لا «مكتمل».

## G. الأثر الخلفي والتراجع

يُملأ القسم 7 من ملف القضية قبل طلب الدمج:

| السؤال | متى يهم |
|---|---|
| هل يتغير حساب مالي **قائم**؟ | إن نعم: كيف عولجت البيانات القديمة؟ ومن راجعها؟ |
| هل يتغير سلوك محسوب سابقًا؟ | رواتب، عمولات، ضوابط تكرار، أرصدة |
| هل يلزم migration؟ | نعم ← إصدار **جديد فوق** الحالي + خطوة `onUpgrade` جديدة فقط (`AGENTS.md` §4.3) |
| هل يلزم تحديث قوائم النسخ الاحتياطي؟ | عند وجود جداول جديدة أو أعمدة مُدرجة |
| السلوك الجانبي المتوقع | سلوك تشغيلي جانبي، تنفيذ مزدوج، تعليمات متكررة |
| خطة التراجع (Rollback) | الـcommit المعاد، أو SQL عكسي، أو Restore من نسخة |

**متى لا يكفي التراجع البرمجي:** إذا وصل الخلل لبيانات عميل مكتوبة فعلًا، فالتراجع لا يصلحها. عندها يلزم **تصحيح بيانات موثّق ومعتمد من صاحب المشروع**، لا تراجع كود.

## I. مصفوفة التحقق للمناطق الحساسة

> `flutter analyze` لا يتحقق من أي مما يلي. كل منطقة تحتاج دليلها الخاص.

| المنطقة | التحقق الإضافي الإلزامي | مرجع قائم للتحقق |
|---|---|---|
| **الترخيص / ربط الجهاز** | لا تمرر مفاتيح حقيقية إطلاقًا — استخدم مولّدات التراخيص التجريبية في `tools/` (مثل `tools/test_license_generator.dart`). تحقق من ثبات Device ID عبر إعادة تشغيل، ومن رفض المفتاح على جهاز مختلف. | `test/unit/hardware_id_service_test.dart` · `test/test_license_activation.dart` |
| **الرواتب والحضور** | شغّل اختبار تكامل الرواتب لإثبات أن إعادة الحساب تُنتج **نفس** القيم القديمة. أكّد أن الاستقطاعات والزواحد والغرامات لم تتغير. | `test/unit/baseline_payroll_parity_test.dart` · `test/unit/payroll_voucher_totals_test.dart` · `test/unit/attendance_deduction_calculator_test.dart` |
| **التصنيع و BOM واستهلاك المخزون** | تحقق من **انحفاظ الكمية**: مُدخل = مُخرج + هالك + فاقد. شغّل سلامة BOM في كل تغيير وصفة أو استهلاك. | `test/unit/manufacturing_bom_integrity_test.dart` · `test/unit/manufacturing_order_completion_test.dart` · `test/unit/manufacturing_scrap_test.dart` |
| **الدفتر والفواتير والنقد وإقفال اليوم** | تحقق من **مطابقة الأرصدة**: مجموع الفواتير = القيود في الدفتر. جرّب الإلغاء والمرتجع والاسترداد الجزئي. تأكد أن عدّاد الفاتورة لا يكرر تسلسلًا بعد أي عملية. | `test/unit/dao/ledger_dao_test.dart` · `test/unit/dao/invoice_dao_test.dart` · `test/unit/invoice_void_test.dart` · `test/unit/return_refund_test.dart` · `test/unit/period_repair_test.dart` |
| **النسخ الاحتياطي والاسترجاع** | تحقق من أن **قوائم الجداول في النسخ تغطي كل الجداول المعرفة في المخطط**، ثم **استرجع فعليًا** نسخة وافحص عدّاد السجلات. أي إضافة جدول/عمود بلا تحديث النسخ = فقدان بيانات صامت. | `test/unit/services/backup_tables_test.dart` |
| **المزامنة والسلوك offline** | تحقق من **Idempotency**: إعادة المزامنة لا تُنتج صفوفًا مكررة، والـoutbox يُفرَّغ ولا يتعطل. | `test/unit/sync_outbox_test.dart` · `test/unit/sync_service_test.dart` |
| **مخطط قاعدة البيانات و migrations** | لا تعديل على step مُطبَّقة (`AGENTS.md` §4.3). اختبر **الترقية نفسها** من الإصدار السابق على ملف DB حقيقي بمحتوى مملوء مسبقًا، وتحقق من حفظ البيانات. | النمط القائم في `test/unit/migration_v77_test.dart` (اختبار `v76 -> v77` يحفظ الطلبات القائمة) · `test/unit/migration_v76_test.dart` |
